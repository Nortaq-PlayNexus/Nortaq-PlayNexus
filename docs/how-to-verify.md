# SIGNAL HASH — how to verify it

The **SIGNAL HASH** shown in the TRANSMISSION STATUS block is not a mystery — it is
a plain, reproducible SHA-256 fingerprint of *public* facts. Anyone can recompute it.

## Definition

```
payload = "SALT=PHANTOMTAPE::SIGNAL::V1"
        + "|OWNER="    + <github username>
        + "|REPOS="    + <public repo count>
        + "|FOLLOWERS=" + <follower count>
        + "|CONTRIB="  + <contributions, rolling 365d via GraphQL>
        + "|DATE="     + <re-broadcast date, UTC, YYYYMMDD>

SIGNAL HASH = first 6 hex chars of SHA256(payload), uppercase
```

The salt is fixed and public, so the only variable inputs are public numbers that change
over time. The hash therefore changes whenever the transmission is refreshed — proof the
block was machine-rebuilt from live data, not hand-edited to look alive.

## Verify locally

```bash
# no network, no tools beyond python3
python3 scripts/signal_hash.py Nortaq-PlayNexus 41 2 893 20260831
# → compare to the SIGNAL HASH line in README.md

# full re-run of the generator (needs a GitHub token for CONTRIB):
#   set GH_TOKEN=... then: python3 scripts/rebroadcast.py
```

If your numbers came from a different snapshot date than the profile's LATEST REBROADCAST
line, the hash will differ — that is expected and correct behavior.

## What it proves (and what it does not)

- Proves the block was generated by the rebroadcast script from current API data. ✔
- Does NOT authenticate identity, and contains no secret material. The salt stores no
  private key and no token — see security.md.

The one-line truth: **read the public numbers, hash them, match the README.**
